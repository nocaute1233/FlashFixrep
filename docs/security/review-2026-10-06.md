# Revisão de segurança — 6 de outubro de 2026

## Modelo de confiança

O executável distribuído ao usuário pode ser inspecionado ou alterado. A API é
a autoridade para autenticação, licenças, bloqueios e ações administrativas.
Nenhum segredo de emissão de chaves pertence ao cliente. Um programa local não
consegue impedir toda modificação ou engenharia reversa; a proteção depende
de validação no servidor e de uma distribuição assinada.

## Alterações desta revisão

- A API faz uma verificação bcrypt mesmo quando o usuário não existe e devolve
  a mesma resposta de acesso negado para usuário ausente, senha errada ou conta
  bloqueada.
- Falhas simultâneas de senha incrementam o contador no banco. Ao atingir
  cinco falhas, a conta fica bloqueada por quinze minutos.
- Sessões administrativas têm token de acesso de cinco minutos e prazo máximo
  de oito horas para renovação. Sessões comuns mantêm os prazos anteriores.
- O cliente administrativo desabilita os botões durante login e emissão de
  chaves para evitar envios duplicados por clique repetido. Mensagens ao usuário
  não expõem detalhes internos das exceções.
- O Gerenciador de Chaves exige o endereço da API na entrada. Ele não escolhe
  automaticamente o servidor local ao receber credenciais administrativas.
- A API continua exigindo HTTPS fora do desenvolvimento em loopback; tokens de
  renovação são trocados por comparação atômica; usuários comuns não acessam
  os endpoints administrativos.
- Cada ativação vincula a licença à chave pública do dispositivo. O aplicativo
  assina desafios de uso único no cadastro, no login e na renovação. A API
  compara a chave pública vinculada antes de emitir ou renovar uma sessão.
- A chave privada é criada como não exportável no armazenamento CNG do Windows,
  preferencialmente no TPM. O provedor de software é usado se o TPM não estiver
  disponível. Uma conta antiga exige redefinição administrativa do dispositivo
  para entrar com o novo protocolo; não há migração baseada apenas no antigo
  identificador de instalação.

## Testes executados

- Cinco logins errados simultâneos retornaram 401. A senha correta também
  retornou 401 após o bloqueio. Usuário inexistente retornou 401.
- Uma conta administrativa de teste emitiu uma chave; uma conta comum ativou
  a chave e recebeu 401 ao tentar emitir outra.
- O bloqueio da conta comum invalidou sua sessão imediatamente.
- O token administrativo de acesso retornado vence em aproximadamente cinco
  minutos.
- O EXE administrativo Windows x64 foi publicado em arquivo único e sua tela
  de entrada abriu para inspeção visual. A política local impediu uma segunda
  execução do arquivo copiado para `dist`, portanto essa cópia final ainda não
  recebeu um teste de login pela interface.
- O teste `tests/DeviceBindingSmoke.ps1` verificou ativação, login no dispositivo
  original, rejeição de outra chave privada com a mesma senha e identificador,
  rejeição de repetição do desafio, renovação de sessão vinculada e troca de
  dispositivo após redefinição administrativa, com invalidação da sessão antiga.

## Pendências antes de produção

1. Publicar a API em um domínio com TLS válido, PostgreSQL protegido, backups
   testados e segredos fora de arquivos versionados. Configurar `FLASHFIX_API_URL`
   com o endereço HTTPS real.
2. Assinar os executáveis com certificado confiável e fixar no cliente a chave
   pública de releases. O EXE gerado nesta revisão está sem assinatura.
3. Adicionar segundo fator às contas administrativas, proteção de borda contra
   tráfego distribuído e monitoramento de eventos de autenticação.
   O login administrativo ainda depende de senha e não tem vínculo ao dispositivo.
4. Fazer revisão independente do código, teste de invasão autorizado e testes
   de recuperação antes de tratar a aplicação como pronta para distribuição.
5. Para várias instâncias da API, mover os desafios de uso único da memória do
   processo para um armazenamento compartilhado com consumo atômico.

A vinculação impede o compartilhamento comum de credenciais entre PCs. Não é
garantia absoluta contra um invasor que controla o PC ativado: ele pode tentar
usar o processo local para assinar desafios, e o provedor de software oferece
proteção menor que o TPM.

O EXE administrativo não contém chave de licença nem credencial de administrador.
Ele precisa de uma API em execução, do endereço informado na tela e de uma
conta administrativa válida.
